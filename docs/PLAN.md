## 1. Что выяснила разведка (это определило архитектуру)

### Bot API MAX не решает задачу «читать все сообщения»

Официальный Bot API (`https://platform-api.max.ru`, домен `botapi.max.ru` устарел,
токен — в заголовке `Authorization`) даёт webhook/long-poll и события
`message_created / message_edited / message_removed / bot_added / bot_started`.
**Но бот видит только то, что адресовано ему**: личку боту, упоминания и команды.
Все сообщения группы он не получает, а в чужие личные диалоги не попадает в
принципе. Плюс: с осени 2025 публикация ботов в MAX доступна только
верифицированным юрлицам РФ.

Вывод: требование «считывает ВСЕ сообщения в MAX» закрывается только
**userbot-режимом** — вход под своим аккаунтом.

### Как сделан userbot

MAX (внутреннее имя **OneMe**) ходит по WebSocket `wss://ws-api.oneme.ru/websocket`,
JSON-RPC вида `{ver, cmd, seq, opcode, payload}`. Протокол отреверсен сообществом,
опкоды публично задокументированы (проект `vkmax`, лицензия MIT). Логин: номер
телефона → SMS-код → постоянный LOGIN-токен. Дальше `opcode 19` синхронизирует
чаты, `opcode 128` приносит **каждое** входящее сообщение, `opcode 64` отправляет
от твоего имени.

Мы **не берём чужую библиотеку в зависимости** — они нестабильны (`pymax`, он же
`maxapi-python`, уже архивирован в read-only). Свой клиент на ~300 строк:
`maxbridge/maxproto/ws.py`. Протокольные знания — из открытой документации vkmax.

### Существующие открытые мосты MAX↔Telegram

| Проект | Что делает | Чего не хватает |
|---|---|---|
| `on112026/max-telegram-bridge` | Playwright + Chromium логинится в веб-MAX, парсит DOM/XHR/WS | тяжёлый (Xvfb+VNC в контейнере), ломается при смене вёрстки |
| `BEARlogin/max-telegram-bridge-bot` | Bot API MAX ↔ TG, темы форума, медиа, правки | видит только адресованное боту |
| `TheMistaKrips/max-telegram-bridge` | Node.js, очередь сообщений | то же ограничение Bot API |
| `MariaShsv/tg-max-bridge` | Python/aiogram/Redis/Docker | связывает **группу с группой**, не «весь аккаунт» |

Все четыре — «тупые релеи». Наше отличие: полный охват аккаунта + AI-слой +
монетизация. Ни у кого из них нет ни сводок, ни приоритетов, ни поиска, ни лицензий.

## 2. Архитектура

```
        MAX (аккаунт или бот)                    Telegram
                 │                                   │
   ┌─────────────┴─────────────┐          ┌──────────┴──────────┐
   │  transports/userbot.py    │          │  telegram/bridge.py │
   │  (свой WS-клиент OneMe)   │          │  (aiogram 3, форум) │
   │  transports/botapi.py     │          │  тема = чат MAX     │
   └─────────────┬─────────────┘          └──────────┬──────────┘
                 │        ┌──────────────┐           │
                 └───────►│ core/router  │◄──────────┘
                          └──────┬───────┘
        ┌──────────┬─────────────┼─────────────┬──────────┐
     rules.py    ai.py       digest.py     search.py   followup.py
   (приоритеты) (Claude)   (что пропустил)  (FTS5)   (не ответил)
                          │
                     db.py (SQLite + FTS5)
```

Транспорт подменяем одной строкой в `.env` (`MAX_MODE=userbot|botapi`) — это же
даёт «легальный» режим для корпоративных продаж и «полный» для личного использования.

## 3. Килер-фичи (моё предложение)

Отсортировано по тому, ради чего человек реально поставит и оставит бота.

1. **Тема = чат.** Каждый чат MAX автоматически становится темой в Telegram-форуме.
   Ответил в теме — ушло в тот же чат MAX **от твоего имени**. Никаких команд.
2. **Стелс-режим.** Читаешь входящие из Telegram, а в MAX они остаются
   непрочитанными: собеседник не видит «прочитано». Выключается флагом.
3. **AI-приоритеты.** Каждое входящее классифицируется (срочное / обычное / шум,
   вопрос / задача / счёт / спам). Срочное — мгновенный пуш в тему «🔥 Важное»,
   остальное копится в дайджест. Правила (`/rule`) + модель Claude.
4. **«Что я пропустил».** `/digest` и авто-сводка в заданный час: по каждому чату —
   3 строки сути и список того, что от тебя ждут.
5. **AI-черновики ответов.** Под каждым важным сообщением — кнопка: бот предлагает
   2–3 варианта ответа с учётом истории чата; правишь и отправляешь одним тапом.
6. **Поиск по всей истории MAX из Telegram.** `/find договор` — FTS5 по всему,
   что бот когда-либо видел. В самом MAX поиск слабый, это ощутимое преимущество.
7. **Радар незакрытых.** «Тебе задали вопрос 3 часа назад и ты не ответил» —
   напоминание с кнопкой «ответить».
8. **Автоответчик и дежурный режим.** Вне рабочих часов / в отпуске — авто-ответ
   по правилу или шаблону, с логом кому что ушло.
9. **Голосовые → текст.** Голосовые из MAX приходят расшифровкой (стыкуется с уже
   имеющимся ASR-пайплайном из txt2word).
10. **Мультиаккаунт + лицензии.** Один сервер обслуживает несколько владельцев;
    лицензионный ключ включает Pro-фичи (AI, мультиаккаунт, экспорт/вебхуки).

Первые 5 — MVP, ради них ставят. 6–9 — удержание. 10 — то, что делает систему товаром.

## 4. Модель продажи (репозиторий открытый, продукт платный)

* Лицензия кода — **AGPL-3.0** (файл `LICENSE`). Открыто, но любой SaaS-форк обязан
  открыть свои изменения. Это стандартный способ открыть код и при этом продавать.
* Кому нужна закрытая интеграция / white-label — **коммерческая лицензия** (отдельный
  файл, напишу на следующем шаге).
* Тарифы: Community (сам себе, 1 аккаунт, без AI) → Pro (AI-фичи, ключ) →
  Team/Hosted (мы хостим, поддержка).
* Технически: `core/licensing.py` — оффлайн-проверка подписанного ключа, гейт на
  Pro-функции. Ключ живёт в `.env`, в репозиторий не попадает.

## 7. Решения владельца (2026-08-19)

1. **Модель распространения — два репозитория.** Публичный `maxbridge`
   (ядро, AGPL) + приватный `maxbridge-pro` (SMS, WhatsApp, вебхук, выпуск
   ключей). Ядро подхватывает платные каналы через точки входа.
2. **Порядок работ** — сначала доделать функции, потом разделять и публиковать.

Юридическая сторона: AGPL связывает тех, кто берёт код, а не автора. Ты
единственный правообладатель, поэтому свою же надстройку можешь лицензировать
закрыто. Появятся сторонние контрибьюторы в публичном репо — потребуется CLA,
иначе их код нельзя будет забрать в закрытую часть.

Трезвая оценка рва: сам код каналов — ~300 строк HTTP-вызовов, переписывается
за вечер. Разделение защищает не секрет технологии, а удобство покупателя.
Реальный ров — хостинг, поддержка и выпуск ключей.
